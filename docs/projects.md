# 駄菓子事業計画書作成 Project

## 1. この文書の位置づけ

この文書は、駄菓子事業計画書を作成するための上位目的文書である。

この文書自体は事業計画書本文ではない。プロジェクト全体の最終成果物は、証拠、仮説、要検証事項、要調査事項、人間確認事項を分離した「駄菓子事業計画書 初版」である。

Loop Engineeringは目的ではなく、事業計画書初版を迷わず、安全に、追跡可能な形で作成するための実行方式である。

## 2. プロジェクト名

駄菓子事業計画書 初版作成プロジェクト

## 3. 上位ゴール

駄菓子を媒介にして、子どもと地域・社会をつなぐ体験事業の事業計画書初版を作成する。

## 4. プロジェクトの目的

このプロジェクトの目的は、駄菓子事業の構想を、実行可能性、検証可能性、安全性、関係者説明可能性を備えた事業計画書初版へ落とし込むことである。

事業計画書初版では、すべてを確定事項として断定しない。決定事項、内部前提、事実、仮説、推論、要検証、要調査を分離し、未確認事項を残したままでも、次に何を確認すべきかが分かる状態にする。

## 5. 最終成果物

最終成果物は `駄菓子事業計画書 初版` である。

初版は、完成版や外部提出版ではない。初版の目的は、事業構想を関係者説明、実証実験設計、追加調査、意思決定に使える形へ整理することである。

| 項目 | 内容 |
|---|---|
| 成果物名 | 駄菓子事業計画書 初版 |
| 主な読者 | ユーザー本人、協力候補者、レビュー担当者 |
| 二次的な用途 | 施設相談、保健所相談、保護者説明、地域団体相談のたたき台 |
| 形式 | Markdownを基本とし、必要に応じてDocs、PDF、スライドへ展開可能にする |
| 完成版との差分 | 法規制、衛生、安全、保険、施設合意などの人間確認必須事項が未完了でも、未確認事項として明示すれば初版に含められる |

## 6. 事業の基本前提

### 6.1 現時点の決定事項

- この事業は、単なる駄菓子販売事業ではない。
- 駄菓子を媒介にして、子どもと地域・社会をつなぐ体験事業として扱う。
- 収益最大化を主目的にしない。
- 実費回収を基本とする。
- 最初は移動式駄菓子屋として小さく始める。
- 最初から本格展開しない。
- 実証実験を通じて、ニーズ、子どもの反応、運営課題、施設側の受け入れやすさを確認する。

### 6.2 重視する体験価値

- 子どもが限られたお金の中で自分で選ぶ体験。
- お金の使い方を学ぶ体験。
- 子ども同士の交流。
- 地域の大人との接点。
- 地域施設や地域団体とのつながり。
- 子どもにとっての思い出づくり。
- 将来的に地元を思い出すきっかけになる場づくり。

### 6.3 検証すべき前提

- 子ども、保護者、施設、地域団体がこの体験価値を必要としているか。
- 移動式駄菓子屋という形式が、施設や地域に受け入れられるか。
- 実費回収で継続可能な商品構成、価格、販売量になるか。
- 安全、衛生、アレルギー、現金管理、責任分界を運用可能な形にできるか。

## 7. 事業計画書初版の章立て

後続エージェントは、Issue成果物を以下の章へ接続する。

| 章ID | 章 | 目的 | 主な入力 | 証拠分類 | 標準処理Levelの目安 |
|---|---|---|---|---|---|
| BP-01 | Executive Summary | 事業全体を短く説明する | 各章の統合結果 | 決定事項、仮説、要検証 | L2 |
| BP-02 | Why / 解決したい課題 | なぜこの事業を行うのかを説明する | ユーザー前提、社会課題、地域課題、観察 | 決定事項、内部前提、仮説、要検証 | L2 |
| BP-03 | 事業コンセプト | 駄菓子を媒介にした体験事業の核を定義する | 事業前提、体験価値、対象者 | 決定事項、仮説 | L2 |
| BP-04 | 対象者とステークホルダー | 子ども、保護者、施設、地域団体を整理する | 既存情報、ヒアリング候補 | 仮説、要検証 | L2 |
| BP-05 | 提供価値 | 各ステークホルダーにとっての価値を整理する | 体験価値、課題仮説 | 仮説、推論、要検証 | L2 |
| BP-06 | 実施形態 | 移動式駄菓子屋の運営イメージを整理する | 出店形式、場所、頻度、必要物 | 仮説、要検証、要調査 | L2。施設合意や実施可否は人間キュー |
| BP-07 | 商品・価格・実費回収 | 商品構成、価格、費用回収の考え方を整理する | 仕入れ、価格、販売数、費用 | 仮説、要検証 | L2 |
| BP-08 | 初回実証実験計画 | 小さく試す条件を整理する | 場所候補、対象、体制、検証項目 | 仮説、要検証、要調査 | L2。実施決定は人間キュー |
| BP-09 | 運営体制 | 人員、役割、当日運営、記録を整理する | 運営案、役割分担 | 仮説、要検証 | L2 |
| BP-10 | リスク・規制・衛生・安全 | 食品衛生、アレルギー、安全、責任を整理する | 公式情報、保健所相談、施設条件 | 事実、要調査、人間確認 | L1/L2。確定判断は人間キュー |
| BP-11 | 収支・継続性 | 実費回収と継続可能性を整理する | 費用、売上、協力体制 | 仮説、要検証 | L2 |
| BP-12 | ロードマップ | 実証後の改善、展開、追加検証を整理する | 各章の未確認事項 | 仮説、要検証 | L2 |
| BP-13 | 未確認事項・Human Check | AIだけで確定できない事項を一覧化する | denylist項目、Blocked項目 | 要調査、人間確認 | L1/L2 |
| BP-14 | エビデンス・Issue対応表 | 根拠と統合元Issueを追跡する | Issue、資料、出典、判断ログ | 全分類 | L1。機械的更新のみL3可 |

## 8. 事業計画書に入れる情報の分類

すべての主張は、以下のいずれかに分類する。

| 分類 | 意味 | 本文での扱い |
|---|---|---|
| 決定事項 | ユーザーまたは人間承認済み資料で明確に決まっていること | 断定してよいが、根拠IDまたは承認者を明示する |
| 内部前提 | 既存資料、壁打ち、親Issue、計画書に基づくこと | 決定事項へ自動昇格させず、前提として明示する |
| 事実 | 公開情報、公式情報、調査資料で確認できること | 出典または確認方法を明示する |
| 仮説 | 未検証だが計画上置く考え | 仮説として書き、検証方法を添える |
| 推論 | 複数の前提からAIが導いた判断 | 前提と推論過程を明示する |
| 要検証 | 実証実験、ヒアリング、現場確認で検証すること | 本文または別表で検証項目化する |
| 要調査 | 法規制、施設ルール、衛生、地域事情など追加調査が必要なこと | 人間キューまたは追加Issue候補として扱う |

決定事項は、既存資料に書かれているだけでは成立しない。承認元または根拠IDがない場合は、内部前提または仮説として扱う。

## 9. L3 denylist / 人間キュー対象

L3無人実行の除外対象は `docs/denylist.json` を正とする。この文書ではdenylist本体を列挙しない。

TriageはL判定時に `docs/denylist.json` を確認し、該当する場合はL3を禁止して人間キューへ昇格する。AIはL1として確認項目を整理し、必要に応じてL2として未確認事項の本文案を作れるが、最終判断はしない。

公式確認先の候補:

- [厚生労働省 食品](https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/kenkou_iryou/shokuhin/index.html)
- [厚生労働省 営業規制（営業許可、営業届出）に関する情報](https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/kenkou_iryou/shokuhin/kigu/index_00010.html)
- [厚生労働省 HACCP](https://www.mhlw.go.jp/stf/seisakunitsuite/bunya/kenkou_iryou/shokuhin/haccp/index.html)
- [厚生労働省 子ども食堂における衛生管理のポイント](https://www.mhlw.go.jp/stf/newpage_00381.html)
- [消費者庁 食品表示](https://www.caa.go.jp/policies/policy/food_labeling/)

## 10. このプロジェクトで作るもの

- 駄菓子事業計画書 初版。
- 事業計画書の各章に接続する統合用素材。
- 根拠、仮説、要検証、要調査、人間確認事項の一覧。
- 章ごとのエビデンス表。
- Issueと事業計画書章の対応表。
- 実証実験で検証する項目。
- 人間確認必須事項の一覧と確認先候補。

## 11. このプロジェクトで作らないもの

- 未確認の法規制、衛生、安全、保険、責任範囲を確定事項として記載した完成版計画書。
- 人間確認なしで外部提出、営業、交渉に使う確定版資料。
- 保健所、施設、保護者、地域団体との合意が完了したかのように見える文書。
- レビュー未完了のIssueを確定情報として統合した計画書。
- 根拠のない社会課題、ニーズ、収支、運営可能性の断定。

## 12. Loop Engineeringを使う理由

この事業計画は、単純な文章生成では不十分である。理由は以下である。

- 事業目的が社会性、体験価値、地域接続を含むため、単純な収益計画に寄せると本質を失う。
- 子ども、保護者、施設、地域、運営者など複数のステークホルダーが関わる。
- 衛生、アレルギー、事故、金銭管理、責任範囲など、AIだけで断定できない論点がある。
- 実証実験で確認すべき仮説が多い。
- 最終事業計画書には、根拠、仮説、要検証、要調査を追跡できる構造が必要である。

したがって、Issueごとに論点を分解し、証拠確認、レビュー、Red Team、Blue Team、Purple Team、Judgeを通してから事業計画書へ統合する。

## 13. Orchestratorの基本方針

本LoopではB方式を採用する。

- Orchestratorは各エージェントの役割、起動条件、入力、出力、禁止事項を前提知識として保持する。
- `agents/*.md` は役割定義の原本、監査基準、実装時の参照仕様として扱う。
- サブエージェントは自律的に別サブエージェントを起動しない。
- サブエージェントは次工程を提案できる。
- 起動可否、順序変更、最終的なStatus採用はOrchestratorが判断する。
- TriageはL1 / L2 / L3分類、denylist該当、状態、必要対応を書き込む。
- Implementer / VerifierはL2 / L3でのみ起動する。
- L1ではImplementer / Verifierを起動しない。
- Verifierは現時点ではReview Agentが兼務し、PR作成前またはAuto-commit前に実差分ベースで `docs/denylist.json` を再確認する。

## 14. サブエージェント出力契約

各サブエージェントは、原則として以下の出力契約に従う。

| 項目 | 内容 |
|---|---|
| target_chapter | 接続先の章ID |
| level | L1 / L2 / L3 |
| denylist_check | denylist該当有無と該当理由 |
| current_state | 現在の状態 |
| summary | 実行内容の短い要約 |
| section_output | 事業計画書に統合可能な本文素材または構造化素材 |
| evidence_class | 決定事項、内部前提、事実、仮説、推論、要検証、要調査の分類 |
| evidence | 根拠、出典、参照Issue、確認方法 |
| risks | リスク、前提破綻、根拠不足 |
| human_check_required | 人間確認が必要な事項 |
| next_agent_recommendation | 次に必要な工程やエージェントの提案 |
| verification_result | L2 / L3での検証結果 |
| pr_url | L2で作成したPR |
| commit_id | L3で作成したcommit |
| human_queue_reason | 人間キューへ昇格する理由 |

サブエージェントの出力は、事業計画書のどの章へ統合されるかを必ず示す。

## 15. Red / Blue / Purple / Judgeの位置づけ

| 役割 | 目的 | 事業計画書への接続 |
|---|---|---|
| Red Team | 失敗要因、反論、リスク、前提破綻を指摘する | 統合禁止、要修正、追加Issue化の判断材料にする |
| Blue Team | Red Team指摘への改善策、補強策、代替案を作る | 本文補強、検証項目化、表現修正に使う |
| Purple Team | Red / Blueの結果から採用、保留、差し戻しを判断する | 統合可否と本文反映方針を決める |
| Judge | PR Ready、Auto Committed、Doneの可否を判定する | 停止位置と完了可否を最終確認する |

## 16. プロジェクトの成功状態

このプロジェクトの成功状態は、以下がそろった状態である。

- 駄菓子事業計画書 初版が存在する。
- 章ごとに、決定事項、仮説、要検証、要調査、人間確認事項が分離されている。
- 各章に、統合元Issueまたは根拠が追跡できる。
- 人間確認必須事項がAI単独で確定されていない。
- 未確認事項が本文または別表で明示されている。
- レビュー済み、または未レビューであることが明確な情報だけが使われている。
- 次に行うべき実証実験、調査、ヒアリング、人間確認が分かる。

## 17. Red Teamチェック

### 指摘

- 上位ゴールを「Loop Engineering実行基盤を整える」と書くと、後続エージェントが管理文書を増やす方向に進み、事業計画書初版の作成へ進まない。
- 「事業計画書本文を作らない」と強く書くと、本文ドラフトや章別素材の作成まで禁止されたと解釈される。
- 事業計画書の章立てがないと、Issue成果物をどこへ統合するか判断できない。
- Whyや地域貢献をきれいな言葉でまとめるだけでは、検証可能な事業計画にならない。
- 実費回収や地域貢献という表現が、食品衛生、営業許可・届出、保健所相談、食品表示、アレルギー、子ども安全の確認を弱める可能性がある。

## 18. Blue Team対応

### 改善方針

- 上位ゴールを「事業計画書初版を作成する」に固定する。
- Loop Engineeringを手段として位置づける。
- 事業計画書の章立てを定義し、各Issue成果物を章IDへ接続する。
- 未確認事項は排除せず、分類した上で本文または別表へ入れる。
- denylist領域はL3無人実行せず、人間確認または追加Issueへ送る。

## 19. Purple Team統合判断

### 採用する方針

- この文書は、事業計画書作成プロジェクトの上位目的文書として維持する。
- 最終成果物は「駄菓子事業計画書 初版」と明記する。
- 「実行基盤を整える」は、目的ではなく準備工程として扱う。
- 後続資料は、必ず事業計画書の章、入力、出力、証拠分類、L分類、denylist、人間確認へ接続する。
- Red / Blue / Purple / Judgeは、事業計画書へ統合してよい素材かを判断するために使う。

## 20. 次に作成する文書

次に作成する文書は、すべて「事業計画書初版を作成するため」に接続させる。

1. `docs/intend.md`: 事業計画書初版のゴール達成条件と判定チェック表を定義する。
2. 完了条件・停止条件文書: どの素材を事業計画書へ統合してよいかを決める。
3. `docs/levels.md`: L1 / L2 / L3の自動化レベルとdenylist参照手順を定義する。
4. `docs/denylist.json`: L3無人実行から除外する条件を定義する。
5. Status遷移・権限定義文書: `Human Queue`、`PR Ready`、`Auto Committed`、`Done` を分ける。
6. `docs/loop.md`: Issue処理から事業計画書統合までの運用方法を定義する。
7. トリアージスキル定義文書: Issueを章ID、証拠分類、担当エージェントへ振り分ける。
8. エージェント定義確認文書: 各エージェントがどの章の素材を作るか確認する。
9. 必要書類チェックリスト: 事業計画書作成に不足している根拠を検出する。
